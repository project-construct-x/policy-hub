# Policy Hub API Contract

Status: current implementation contract; the policy model and constraint types remain provisional.

This document captures the shared behavior expected by the frontend and backend. The backend's
Springdoc-generated OpenAPI document at `/v3/api-docs` is the machine-readable API description;
Swagger UI is available at `/swagger-ui.html`. Both implementations and the generated OpenAPI
document must conform to this contract. A mismatch is a defect or an unresolved decision, not an
automatic reason to prefer either implementation.

## Ownership and change process

- Frontend and backend are equally important parts of the product. The frontend was implemented
  first and used MirageJS so it could be developed independently while the backend was being built.
  This history does not make either implementation authoritative over the other.
- When behavior or types disagree, check this contract and the relevant user/domain requirement.
  Do not silently change one side to match the other. Resolve unclear or breaking changes with the
  project owner, then update this contract, backend OpenAPI annotations/tests, and frontend models,
  service, Mirage routes, and tests together.
- Additive, backward-compatible changes may be made within `/api/v1`. Changes that break existing
  clients require an explicit migration/versioning decision before implementation.
- Keep the OpenAPI description, backend behavior, frontend client/mock behavior, and this document
  aligned. The OpenAPI schema describes wire shapes; this document also records domain semantics
  that are not fully expressible in OpenAPI.

## Base path and authentication

- Resource base path: `/api/v1/policies`.
- Policy endpoints require HTTP Basic authentication in the current implementation. The
  development credentials are documented in `backend/README.md`; do not treat them as production
  credentials. The production authentication method remains undecided.
- `/v3/api-docs`, Swagger UI, and the health/info actuator endpoints are public in the current
  backend configuration.
- The Angular development server proxies `/api` to the backend. Browser clients should use the
  configured relative API base URL; do not add a CORS dependency for the local development flow.

## Endpoints

| Method and path | Request | Success | Relevant errors |
|---|---|---|---|
| `GET /api/v1/policies` | Query: `page`, `size`, `sort` | `200`, paginated `Policy` response | `400` for invalid query parameters; `401` unauthenticated |
| `GET /api/v1/policies/{id}` | `{id}` is the backend UUID | `200`, `Policy` | `404` not found; `401` unauthenticated |
| `GET /api/v1/policies/{id}/odrl` | `{id}` is the backend UUID | `200`, ODRL `PolicyDefinition` | `404` not found; `401` unauthenticated |
| `POST /api/v1/policies` | `CreatePolicyRequest` JSON | `201`, created `Policy` | `400` invalid request; `409` duplicate `policyId`; `401` unauthenticated |
| `PUT /api/v1/policies/{id}` | Full `UpdatePolicyRequest` JSON; all editable fields required | `200`, updated `Policy` | `400` invalid request; `404` not found; `409` duplicate `policyId`; `401` unauthenticated |
| `DELETE /api/v1/policies/{id}` | `{id}` is the backend UUID | `204`, no response body | `404` not found; `401` unauthenticated |

There is no `PATCH` endpoint. Search and filtering are not part of the collection API. Do not imply
that a filtered or searched page represents the full collection.

## Policy representation

The current JSON fields are:

| Field | Request | Response | Meaning and constraints |
|---|---|---|---|
| `id` | Not accepted | Required | Backend-generated UUID; resource identifier used in routes. |
| `policyId` | Required | Required | Client-defined business identifier, non-blank, at most 200 characters, unique. Used as the ODRL `@id`. |
| `category` | Required | Required | `ACCESS` or `CONTRACT`. |
| `constraints` | Required | Required | Ordered JSON array of supported constraint objects; see below. An empty array is valid. |
| `legalText` | Required | Required for current records | Non-blank German legal text generated by the frontend. The backend persists and returns it unchanged; it does not generate or validate its legal meaning. The frontend read model currently tolerates it being absent on legacy records. |
| `createdAt` | Not accepted | Required | Backend-generated ISO-8601 timestamp. |
| `updatedAt` | Not accepted | Required | Backend-generated ISO-8601 timestamp, updated on edits. |

`POST` and `PUT` use the same editable fields: `policyId`, `category`, `constraints`, and
`legalText`. Updates replace these editable values; clients must send the complete request body.
The backend controls `id`, `createdAt`, and `updatedAt`.

## Constraint contract

Each constraint is a JSON object with a supported `type`. A constraint type may occur at most once
in a policy. The current backend accepts all three types in both categories (`ACCESS` and
`CONTRACT`). Constraint order is retained and determines ODRL operand order.

| Type | Required fields | Current validation |
|---|---|---|
| `MEMBERSHIP` | `value` | Must be the string `active`. |
| `DATE_RANGE` | `startDate`, `endDate` | ISO calendar dates in `YYYY-MM-DD`; neither date may be before the backend's current local date; `startDate` must not be after `endDate`. |
| `FRAMEWORK_AGREEMENT` | `agreement` | Must be a non-blank string. |

Unknown constraint types are rejected. Constraints are provisional domain concepts and may change
when the Construct-X policy model is finalized; coordinate such changes across both applications.

## Pagination

The collection response uses Spring's `Page` JSON shape:

```json
{
  "content": [],
  "totalElements": 0,
  "totalPages": 0,
  "size": 20,
  "number": 0,
  "numberOfElements": 0,
  "first": true,
  "last": true,
  "empty": true
}
```

- `page` is zero-based and defaults to `0`; `size` defaults to `20`.
- `sort` uses Spring Data syntax, for example `updatedAt,desc`. Unspecified sort order is not a
  stable ordering guarantee; clients needing deterministic ordering should request one explicitly.
- `number` in the response is zero-based. `content` contains only the requested page.
- Search/filter parameters are not currently supported by the backend.

## ODRL representation

`GET /api/v1/policies/{id}/odrl` returns an EDC-compatible ODRL `PolicyDefinition` generated from
the stored policy. Its `@id` is the business `policyId`, not the backend UUID. The category selects
the action (`ACCESS` maps to the Construct-X `access` action; `CONTRACT` maps to `odrl:use`).

Current constraint mappings:

| Constraint | ODRL left operand | Operator | Right operand |
|---|---|---|---|
| `MEMBERSHIP` | `cx:Membership` | `odrl:eq` | `value` |
| `DATE_RANGE` start | `cx:DataUsageStartDate` | `odrl:gteq` | `startDate` |
| `DATE_RANGE` end | `cx:DataUsageEndDate` | `odrl:lteq` | `endDate` |
| `FRAMEWORK_AGREEMENT` | `cx:FrameworkAgreement` | `odrl:eq` | `agreement` |

The namespace/context and complete JSON shape are defined by the backend mapper and verified by
backend mapper tests. The frontend Mirage route must return the same wire shape as this endpoint;
keep its mapper and tests aligned with backend output.

## Errors

Application errors use this JSON shape:

```json
{
  "timestamp": "2026-10-09T12:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "constraints[0].agreement is required",
  "path": "/api/v1/policies"
}
```

The backend currently uses `400` for malformed or invalid input, `404` for missing policies, and
`409` for a duplicate `policyId`. Authentication failures are handled by Spring Security and are
not guaranteed to use the application error body above. Clients should branch on HTTP status and
must not depend on the exact wording of `message` for program logic.

## Contract checks when changing the API

- Update Spring controller/DTO validation and OpenAPI annotations; verify the generated document at
  `/v3/api-docs` describes the changed wire contract.
- Update backend controller/service/mapper tests for request, response, validation, and error
  behavior that changed.
- Update frontend shared models, HTTP service, Mirage routes/data, and relevant frontend tests.
- Keep ODRL output parity between backend and Mirage where the UI uses that endpoint.
- Treat changes to required fields, identifiers, enum values, pagination semantics, status codes, or
  ODRL IRIs/operators as contract changes and document compatibility/migration impact.
